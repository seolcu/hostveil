    Measured results

    The September 11, 2026 rerun measured Hostveil alongside Lynis, the CIS Docker Benchmark, a TCP scan from the Docker bridge, and the kernel’s listening sockets. The tables include the changes that helped, the risks that remained, and the state rollback did not restore.

    What this measurement establishes

    Hostveil’s own score increasing after its own fixes only establishes consistency. Independent tools help check whether the host changed too. This is one seeded configuration on disposable VMs, not a security guarantee or a survey of production servers.

    This final rerun supersedes September 10 for reporting. The fixes/rollback experiment and the control experiment each used a fresh VM, without manual pre-hardening. See the run record and limitations, the raw fixes/rollback JSON, and the raw control JSON. Earlier runs remain in the repository.

    The measured host

    The seed runs Nextcloud with PostgreSQL, Jellyfin with Redis, and Portainer with Watchtower. It permits root SSH login, disables the firewall and automatic updates, and seeds weak accounts, agent configurations and kernel settings. All 13 domains ran; 13 completed without a coverage gap.

    Five phases

    PhaseAction before measurement
    beforeFreshly seeded host
    afterhostveil fix --all --yes; Auto fixes, before service restarts
    restartedRestart/reload services and run docker compose up -d for each stack
    reviewedhostveil fix --all --review --yes; then restart/reload again, including irreversible exec actions
    restoredRoll back all checkpoints, then restart/reload; exec actions remain outside rollback

    File edits do not all take effect at once. File modes can change immediately, while a running container keeps its old port mapping until recreated. SSH changes that can cut off access require Review. Showing every phase keeps the effect of edits, restarts and accepted Review actions distinguishable.

    What changed, and what did not

    After the first restart, the scan stopped reaching 5432, 6380, 8080, 8096. After Review, only 22 answered. The kernel still listed 22, 6379 as wildcard/routable listeners: Redis on 6379 remained bound while the scan recorded it as filtered. A binding and a successful TCP connection are different observations. Port 2375 was already refused before any fix.

    CIS warnings 5.14, 5.26, 5.3 cleared at restart, and 5.11 (container memory limits) cleared after Review. Warning 5.32 also appeared, so four cleared warnings produced a net decrease of three. Check 5.3 is a measurement caveat: docker-bench accepts a non-empty SecurityOpt; no-new-privileges can satisfy that test without configuring SELinux.

    Lynis improved at the Auto phase as well as after restarts and Review. Its warnings changed: AUTH-9283, PKGS-7392 cleared and KRNL-5830 appeared. AUTH-9204 and AUTH-9208 remained; both concern the seeded second UID-0 account, which Hostveil reports as accounts.uid0 and leaves for manual handling.

These results describe the measured commit, not the current fix registry’s coverage.

    Unexplained control-scan discrepancy

    The control scan reported fewer reachable ports even though ss listed the same seven wildcard/routable ports before and after. The run did not establish the cause. The observed drop in reachability must not be presented as proof that the control closed those bindings.

    All checkpoint rollbacks completed without a reported failure, but the host did not return to its full original state. The paths that did not match their before-state hashes were /etc/issue, /etc/issue.net, /etc/shadow.

    PathRecorded explanation
    /etc/shadowssh.emptypasswords locks an empty-password account with passwd -l, an exec action with no restore checkpoint.
    /etc/issue, /etc/issue.netHostveil’s own edits were rolled back, but the package installation triggered by updates.disabled also upgraded base-files and rewrote the banners. The September 10 investigation traced this through dpkg.log; September 11 reproduced the same residue without repeating that investigation.

    Before-state hashes come from the live host before fixes, not from Hostveil’s checkpoints. The run also records paths whose before-state was unobserved: /usr/bin/x86_64-linux-gnu-as, /usr/bin/x86_64-linux-gnu-as (0755), /usr/bin/x86_64-linux-gnu-ld.bfd, /usr/bin/x86_64-linux-gnu-ld.bfd (0755). They are not evidence of successful restoration.

    After rollback, the score is 32, compared with 28 before. The scan reaches 22, 5432, 6380, 8080, 8096, 9000, while the kernel lists 22, 5432, 6379, 6380, 8080, 8096, 9000. Redis remains filtered and Portainer’s 9000 now answers. Equal port counts do not mean equal ports, and rolling back files does not undo package installs, account locks or firewall commands.

    Limits of the result

    This is a full Auto-plus-Review experiment, including irreversible actions. It is not the outcome of fix --all alone. The seeded host is intentionally weak, all domains ran, and the systemd and proxy axes already scored 100 before fixes. Domain availability does not prove that every rule was exercised.

    The TCP scan originates on the Docker bridge, not on the public internet. Routing, filtering and timing can change its observations; it does not test cloud security groups or every possible network path. The control discrepancy remains unresolved. These instruments measure configuration and reachability, not breach probability.

    The September 10 and 11 fixes/rollback runs reproduced the same scores, finding counts, auditor deltas and unrestored paths. That is repeatability on this fixture. Package repositories, images and vulnerability databases can change future runs; comparisons across Hostveil versions also include scoring and coverage changes.

    Reproduce it

    Use a disposable VM from scripts/measure/Vagrantfile. The scripts deliberately weaken and then modify that host. See the linked run record for the exact environment. Run the fixes experiment and the control on separate freshly seeded VMs.

    # Inside the first disposable VM, using the recorded source commit:
sudo scripts/measure/seed.sh
sudo scripts/measure/run.sh -c -p cisc-w2026-seeded-v2 /tmp/fixes.json

# Inside a separate, freshly provisioned disposable VM:
sudo scripts/measure/seed.sh
sudo scripts/measure/run.sh -c -C -p cisc-w2026-control-v2 /tmp/control.json

    Both recorded runs passed check.py. Its rollback check permits residue when Review includes actions marked not reversible; exit 0 does not mean 100% file restoration. The website’s figures are checked against the published raw run, with the control figures checked against their separately named file.
