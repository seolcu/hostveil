이 문서는 hostveil 저장소의 소스와 `scripts/measure/` 하네스를 이번 세션에서
직접 실행해 얻은 수치만 담는다. README/문서/웹사이트에 이미 적힌 숫자는
어디에도 재사용하지 않았다. 원본 로그/JSON은 같은 디렉터리의
`2026-09-10-cisc-w2026-*` 파일들이고, 구조화된 전체 데이터는
`2026-09-10-cisc-w2026.json`이다.

`internal/docs/measurements_test.go`가 이 파일을 사이트 수치의 기준으로
삼지 않도록 했다.

## 실험 A — 조치 전후 비교

`scripts/measure/run.sh -c -p cisc-w2026-seeded`. 시점 매핑: before=S0,
after=S1(`fix --all --yes` 직후, 재시작 없음), restarted=S2(+재시작),
reviewed=S3(+`fix --all --review --yes`+재시작). `check.py`의 두 약속(롤백
충실도, 점수 상승) 모두 통과 (exit 0).

|---|---|---|---|---|---|---|---|---|
| S0 (before) | 28/100 | 140 | 40/41/59 | 57 | 4 / 37 | 15 | 22,5432,6379,6380,8080,8096 (6) | 동일 (6) |
| S1 (after) | 37/100 | 97 | 29/28/40 | 63 | 4 / 33 | 15 | 22,5432,6379,6380,8080,8096 (6) | 동일 (6) |
| S2 (restarted) | 40/100 | 83 | 28/19/36 | 66 | 4 / 33 | 13 | 22,6379 (2) | 22,6379 (2) |

S3에서 `ss`는 6379를 wildcard로 표시하지만 외부 스캔은 도달 불가로 보고했다.
원인: S3 시점에 native redis(6379)의 바인드 자체는 아직 `bind 0.0.0.0`
그대로였고(리뷰 조치가 아직 그 파일을 안 건드린 시점), 그 시점 ufw는 이미
enable된 뒤라 22만 허용하고 있어 6379는 실제로 막혀 있었다 — `ss`(바인드
여부)와 외부 스캔(도달 가능성)이 서로 다른 질문에 답하고 있을 뿐, 둘 다
정확하다.

**S3 이후 롤백 완료 시점(restored)의 재측정**은 실험 B에서 별도로 다룬다.

## 실험 A/B — 롤백 후(restored) 상태와 ss/외부스캔 불일치 상세

롤백을 전부 마친 뒤에도 점수는 원점(28)으로 돌아가지 않고 32/100이었다.
원인: `ufw enable`처럼 파일 편집이 아닌 조치(exec, 체크포인트 없음)는
hostveil 자신도 되돌릴 방법이 없다 — 이는 결함이 아니라 설계된 동작이다
(`reviewed.not_reversible=16`).

**ss vs 외부 스캔 불일치(restored 시점)**:

| 포트 | `ss -ltn` wildcard 바인드 | 외부 스캔 도달 |
|---|---|---|
| 22 | O | O |
| 5432, 6380, 8080, 8096, 9000 (모두 Docker 퍼블리시 포트) | O | O |
| 6379 (native redis, 비-Docker) | O | **X** |

직접 확인한 근거:
- `ufw status verbose` → `active`, `Default: deny (incoming)`, 허용 규칙은
  `22/tcp ALLOW IN Anywhere`뿐.
- `/etc/redis/redis.conf`는 롤백으로 seed.sh 원본값(`bind 0.0.0.0`,
  `protected-mode no`)까지 정확히 복원됨.

**결론**: ufw는 호스트 자체 INPUT 체인만 필터링하고, Docker가 퍼블리시한
포트는 Docker 자신의 iptables DNAT/FORWARD 규칙이 ufw보다 먼저 적용돼
우회한다. 이는 hostveil의 `firewall.docker-bypass` 파인딩이 정확히 지적하는
그 메커니즘이며, 이번 실측에서 실제로 재현되었다. `ss`와 외부 스캔 둘 다
맞는 답을 하고 있고, 좋아 보이는 쪽만 골라 적지 않았다.

## 실험 C — 대조군 (CIS Docker Benchmark + Lynis, hostveil 조치 없음)

**계정 삭제 단계 검증**: `control.sh`의 `userdel -f breakglass` 실행 시
`userdel: user breakglass is currently used by process 1` 경고가 출력됐다.
이 경고는 콘솔에 그대로 찍혔고(`2>/dev/null`로 숨겨지지 않음), 실제
삭제 여부를 `getent passwd breakglass`(종료코드 2, 항목 없음)와
`id breakglass`(`no such user`, 종료코드 1)로 직접 확인한 결과 **계정은
실제로 삭제됐다**. 경고 메시지만 보고 성공/실패를 판단하지 않았다.

**중요한 실행상 정정**: 처음에 계정 삭제만 별도 검증하려고 `control.sh`를
수동으로 한 번 실행했는데, 이 때문에 VM이 더 이상 "순수 시드 상태"가
아니게 되어 `run.sh -C`가 자체적으로 수행하는 before 측정이 오염될 뻔했다.
VM을 재시드한 뒤 `run.sh -C`를 다시 깨끗하게 실행해 아래 표를 얻었다.
수동 `control.sh` 1회 실행 로그는 계정 삭제 검증 증거로만 남기고 아래
before/controlled 비교에는 포함하지 않았다.

**메모리 부족으로 인한 재시도**: 실험 C의 `run.sh -C` 실행은 이 개발
머신의 메모리 부족(브라우저/채팅/게임 클라이언트가 대부분의 14GB RAM을
점유)으로 두 번 강제 종료되었다. 두 시도 모두 경로 해싱 초기 단계에서
죽어 측정 데이터는 전혀 생성되지 않았고, 사용자가 호스트 메모리를 정리한
뒤 세 번째 시도가 성공했다(`check.py` exit 0). 이 재시도는 "좋은 결과만
남기려는" 재실행이 아니라 순수 리소스 문제였음을 밝혀둔다.

**`ports` 축 악화(24→12)에 대해**: `listeners_public_tcp` 델타를 보면

잡혔다. control.sh는 포트/ufw/compose 파일을 전혀 건드리지 않으므로
control.sh의 조치 자체가 원인일 수 없다.

**추가 조사(2026-09-11, 사용자 요청으로 원인 재확인 시도)**: 별도로 새
VM을 띄워 두 가지 가설을 직접 검증했다.

1. *"호스트 kill이 원격 프로세스까지 죽이는가?"* — 실제 사고를 그대로
   재현: `vagrant ssh -c 'run.sh -C ...'`를 실행해 실제 kill이 났던 지점과
   동일한 로그 줄("hashing the before-state...")까지 도달시킨 뒤 로컬
   wrapper 프로세스를 강제 종료했다. **원격 `run.sh`는 죽지 않고 PID 1의
   고아 프로세스로 계속 살아남았다** — 이는 이번에 새로 발견한, 하네스/
   구동 방식의 실제 결함이다. 다만 그 고아 프로세스는 진행 중이던
   `hostveil scan --json`(읽기 전용) 하나를 마친 뒤 다음 stdout 출력에서
   끊긴 SSH 파이프에 막혀(SIGPIPE로 추정) 곧 스스로 종료됐고, `control.sh`나
   `docker compose` 호출에는 도달하지 못했다. 즉 이 경로는 실제로
   컨테이너 상태를 건드리기 전에 죽는 것으로 관찰되어, 포트 9000 불일치의
   **충분한 원인으로 보기는 어렵다**.
2. *"portainer가 뜨는 데 오래 걸리는가?"* — 완전히 새로 시드한 VM에서
   `seed.sh` 완료 직후 바로 확인한 결과, 포트 9000은 **이미 51초 만에
   바인드되어 있었다**(`RestartCount=0`, 헬스체크 없음). compose가
   `ports: ["9000:9000"]`를 헬스체크/`depends_on` 없이 정적으로 매핑하므로
   호스트 쪽 `docker-proxy` 리스너는 앱 내부 초기화 완료 여부와 무관하게
   컨테이너 시작과 거의 동시에 열린다. `run.sh -C`가 경로 해싱 + 5종
   계측을 거쳐 실제 `ss -ltn`을 확인하기까지 걸리는 시간은 이보다 훨씬
   기므로, "아직 안 떴을 것"이라는 원래 가설도 일반적으로는 설득력이
   약하다.

**결론**: 두 가설 모두 원래 실험 C의 불일치를 완전히 설명하지 못했다.
**근본 원인은 확정하지 못했다** — 문제의 VM은 이미 폐기됐고 컨테이너
시작 시점의 경쟁 상태(race)는 본질적으로 비결정적이라 동일 조건을
재현할 수 없었다. 다만 이번 조사로 새로 확인된 사실 두 가지는 그 자체로
기록해둘 가치가 있다: (1) `vagrant ssh` wrapper를 호스트에서 죽여도
게스트의 원격 명령은 죽지 않는다(하네스를 이런 식으로 구동할 때의 실제
결함), (2) portainer의 포트 바인드 자체는 일반적으로 느리지 않으므로,
같은 스택에서 실제로 관찰된 컨테이너 조기 크래시(`mgmt-watchtower-1`이
"client version 1.25 is too old" 오류로 시작 직후 종료 — 이 재현
세션에서 독립적으로 관찰됨)류의 **일시적 시작 실패 쪽이 더 유력하지만
증명되지는 않은 설명**으로 좁혀졌을 뿐이다.
