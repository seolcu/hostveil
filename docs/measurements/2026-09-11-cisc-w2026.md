# CISC-W 2026 실측 데이터 — 클린 재실행 (2026-09-11)

**이 문서가 최종본이다.** `2026-09-10-cisc-w2026.md`는 (1) 실험 C에서
`control.sh`를 미리 손으로 한 번 돌려 자체 before 측정이 오염됐던 문제,
(2) 개발 머신 메모리 부족으로 2회 강제종료 후 세 번째 시도로 성공했던
이력이 있어, 사용자 요청으로 **VM을 완전히 새로 띄워 A/B·C 둘 다 처음부터,
수동 개입이나 재시도 없이 한 번에** 다시 실행했다. `2026-09-10` 파일들은
투명성을 위해 그대로 커밋에 남겨두되, 보고 대상 수치는 이 문서를
기준으로 한다.

이번 실행은 두 실험 모두 **첫 시도에 성공**했다(`RUNSH_EXIT=0`, 재시도
없음). 실험 A/B 도중 노트북이 절전모드에 들어갔다 복귀한 일이 있어, 그
세션의 VM은 신뢰하지 않고 폐기한 뒤 완전히 새 VM으로 다시 시작했다.

**이번 실행에서 새로 관측된 ss vs 외부 스캔 불일치**: `ss -ltn`은
before/controlled 양쪽 다 동일하게 7개 포트(22,5432,6379,6380,8080,8096,9000)를
wildcard 바인드로 보고했다(**전혀 변화 없음**). 그런데 외부 스캔 도달
포트는 before 7개 → controlled 2개(22,6379)로 줄었다. control.sh는 ufw/
iptables/compose 파일을 전혀 건드리지 않으므로 바인딩 자체가 안
바뀌었는데 도달 가능성만 바뀐 것이다. **이번 세션에서는 이 원인을 규명하지
않았다** — 후보로는 외부 스캔 컨테이너 자체의 타이밍 기반 판정 방식의
일시적 결함, 또는 `restart_services()`의 `docker compose up -d` 호출이
컨테이너를 재생성하지 않고도 도커 브리지/NAT를 일시적으로 재초기화했을
가능성 등이 있으나, 증거로 확정하지 못했으므로 사실만 그대로 기록한다.

**계정 삭제 검증**: `userdel: user breakglass is currently used by process 1`
경고가 이번에도 동일하게 출력됐다. 2026-09-10에서 `getent`/`id`로 실제
삭제를 직접 확인했고 메커니즘(GNU `userdel -f`가 PID-1 UID 검사를 강제로
통과)은 VM 인스턴스에 의존하지 않으므로 이번엔 재검증하지 않았다.
