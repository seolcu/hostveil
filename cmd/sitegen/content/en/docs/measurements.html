Measured results

hostveil’s score going up after hostveil’s fixes proves nothing: the same code decides what a finding is, what fixing it means, and what the number should be afterwards. So this page reports what other people’s tools saw on the same host, before and after — including the ones that did not move, and one that moved for the wrong reason. Every figure here comes out of a committed run you can reproduce.

Why not just report the score

A self-consistent scanner is easy to build and worthless. If hostveil declares a port binding a finding, edits the Compose file, re-reads the file it just wrote, and awards itself points, nothing about that loop touches your server’s security. Every step could be internally correct and the whole thing still be theatre.

The only way out is instruments that were not written by us and do not share our opinions. Three of the four below were written by other people for other reasons; the fourth is the kernel’s own list of listening sockets, which has no opinions at all.

What follows is one run against one deliberately misconfigured host. It is evidence, not a benchmark: read what this does not show before quoting any of it.

The host

A container seeded with the misconfigurations self-hosters actually ship: three Compose stacks totalling seven services with published ports, privileged containers and no no-new-privileges; an SSH drop-in permitting empty passwords, root login and password authentication; a second UID 0 account; two AI agent runtimes with their config world-readable; a Docker daemon on an unauthenticated TCP socket; and three datastores — PostgreSQL, Redis and Memcached — reachable on 0.0.0.0 with no firewall in front of them.

Four phases, and why two of them are separate

Every Auto fix hostveil applies is a file edit. That is what makes it reversible, and it is also why none of it is in force the moment it lands: a running container keeps the port mapping it was created with, and a daemon keeps serving from the config it already loaded.

So the host is measured four times.

PhaseThe host is…
beforeAs seeded.
afterhostveil fix --all --yes has run. Files changed; nothing restarted.
restarteddocker compose up -d per stack. The services have read the new files.
restoredEvery checkpoint rolled back, and the services restarted back out of the change.

Reporting only after would say the independent instruments saw nothing, which is true and reads as though the fixes did nothing. Reporting only restarted would quietly credit hostveil with a restart it does not perform and deliberately does not offer as an Auto fix — restarting a service is not reversible and cannot be checkpointed. The gap between those two columns is the single most useful thing on this page.

What moved

The kernel’s listening sockets. Five ports left the wildcard address for loopback: 5432, 6380, 8080, 8096, 9000. That is Postgres, Redis, Nextcloud, Jellyfin and Portainer, and it is the least arguable result on this page — nothing interpreted anything, the bind address changed.

The CIS Docker Benchmark. Three checks cleared: 5.14, 5.26, 5.3. 5.14 is incoming container traffic is bound to a specific host interface and 5.26 is the container is restricted from acquiring additional privileges — the port bindings and no-new-privileges respectively, confirmed by a tool that has never heard of hostveil. 5.3 is a different story; see below.

hostveil’s own ports axis. Worth noting because it moved in the restarted column and not the after one: the exposed-services checker reads live sockets rather than files, so it does not credit a change until the change is real. Its own container axis moved a phase earlier, because that one reads Compose files.

What did not move

Lynis moved by one point, and it is right not to move further. The index went 56 → 57, held there through the restart, and came back to 56 when the fixes were rolled back — so the point is attributable rather than noise. But not one of its 41 suggestions cleared, and there are two reasons, neither of which is that the fixes did nothing. Lynis rolls all of SSH into a single composite suggestion covering a dozen options at once; hostveil’s Auto set changed three of them and left PermitRootLogin and PasswordAuthentication to Review, because turning those off can end the session you are issuing the command from. And most of what Lynis wants — a malware scanner, a file-integrity tool, a hardened boot loader, a login banner — is not in hostveil’s scope at all. A tool that measures a superset of your work will mostly show you the part you did not do.

The external scan did not move, and that is the fixture’s fault rather than a result. The seeded containers are stubs that publish ports without serving them, so a connection to 8080 is refused by the backend and the scan reads it as closed while the wildcard binding is still wide open. That is precisely why the listening-socket instrument is on this page: an external scan reports what answers, and a port that is bound but silent becomes exposed the moment something starts serving behind it.

Nothing moved in the after column except hostveil’s own numbers and that single point of Lynis’s index. Twenty-seven fixes had been applied and five files on disk had changed, and the CIS Docker Benchmark, the external scan and the kernel’s socket table all reported an identical host. This is the honest shape of a file-editing fixer, and it is the reason the restart column exists.

One check cleared for the wrong reason

CIS 5.3 is ensure that, if applicable, SELinux security options are set, and it cleared. SELinux was not configured — docker-bench implements that check by asking whether HostConfig.SecurityOpt is non-empty, and no-new-privileges lands in exactly that field. So hostveil turned a genuine HARDENING improvement into a passing SELinux check on a host with no SELinux.

It is on this page because it is the failure mode the page is about, arriving through the independent instrument rather than through ours. An external number moving is not proof that the underlying property changed. Three of the four instruments here were consistent; the fourth agreed for a reason that does not survive being read.

Rollback fidelity

Not a security measurement — a claim about the recovery layer, and the one that has to hold before any of the rest is worth having. hostveil asks an operator to let it edit files on a server, and “you can undo it” is the entire reason that is a reasonable thing to ask.

Paths watched19
Changed by the fixes5
Restored byte for byte5
Checkpoints rolled back27
Fidelity100%

The hashing is deliberately not done against the checkpoints. A checkpoint records what hostveil believes it backed up, so comparing a restored file against it asks only whether hostveil agrees with itself. The candidate paths come from the scan — every file a finding points at, plus every entry of /etc/sysctl.d, because a fix that creates a file is invisible in a before-state that only lists what exists — and they are hashed on the live filesystem before anything is applied. That is the state a rollback has to reproduce.

The restored column of the results table is the same claim measured a second way, by instrument rather than by hash: every number came back to where it started.

What this does not show

One host, one configuration. A seeded container, not a survey. It says what happened here; it does not predict what happens on yours.

Auto fixes only. fix --all applies exactly the fixes classified Auto. The Review and Manual findings — PermitRootLogin, the firewall, the Docker TCP socket, the second root account — were all left in place, and every one of them is a bigger change than anything measured above. This is a floor, not a ceiling.

Two domains did not run. Trivy was not installed, so the CVE axis is N/A; the container has no systemd, so service hardening is too. Neither is represented in any number here.

The containers are stubs. They publish ports without serving them, which is what blinded the external scan. A fixture that ran real services would give that instrument something to see.

Nothing here measures whether you get breached. Every instrument on this page, ours included, measures configuration. That is the honest limit of what a scanner reading files can claim.

Reproduce it

The harness is in the repository, and it edits the host it runs on — point it at a container or a throwaway VM, never at your own machine.

git clone https://github.com/seolcu/hostveil && cd hostveil
go build -o /usr/local/bin/hostveil ./cmd/hostveil

# Lynis and docker-bench-security are optional; a missing one is
# recorded as absent rather than passed over.
sudo scripts/measure/run.sh -p seeded /tmp/measurement.json

Committed runs live in docs/measurements/, and every figure on this page is checked against the newest of them by a test — a stale number here is a failing build, not something a reader has to catch. The harness also runs nightly, where it asserts only the two claims that are promises rather than observations: that rollback restores every changed file exactly, and that hostveil’s own score moved at all.
